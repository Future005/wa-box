# WA Box

Schedule WhatsApp messages to your existing WhatsApp groups, with random gaps between groups, for a whole team.
Lives at **https://wabox.example.com/wabox**.

- **Engine:** our own small service (`engine/`) built on [`whatsapp-web.js`](https://github.com/pedroslopez/whatsapp-web.js): a real headless Chrome running WhatsApp Web. Never Baileys.
- **App:** small Node.js app (scheduler + web page), SQLite, India time (IST) everywhere.
- **Deploy:** Coolify, Docker Compose build pack, this repo.

```
Team (browser) ──HTTPS──▶ Coolify proxy ──▶ wabox (scheduler + UI) ──private network──▶ engine (headless Chrome → WhatsApp Web)
```

Only `wabox` is public. The engine has no domain and no published port, and every call needs its API key.

## Using it

1. **Log in** at `/wabox`. First admin is `admin@example.com`; the password is Coolify's generated `SERVICE_PASSWORD_ADMIN`
   (app → Environment Variables). You must change it on first login.
2. **WhatsApp tab (admins):** press *Connect / show QR*, then on the phone: WhatsApp → Settings → Linked devices → Link a device → scan.
   Use a spare number if you can.
3. **Groups:** only groups whose name contains your keywords (default *Acme Academy*, *Masterclass*; change in Settings) are saved. The list is read from WhatsApp only when someone presses *Sync from WhatsApp* (plus once automatically after connecting), so the picker loads instantly.
4. **Schedule tab:** pick groups, write the message (optional image), choose date + time (IST), optional weekly repeat,
   and the random gap range. The preview shows when the last group will get it.
4. **Upcoming:** edit, *Send now*, or cancel. Live per-group progress.
5. **History:** every group, every send, with errors.
6. **Settings (admins):** it starts in **Dry run** (nothing is sent). Turn it off when you're ready.
7. **Team (admins):** add people as *member* (schedule only) or *admin*. They set their own password on first login.

## Safety rules (enforced on the server, can't be turned off)

- One job at a time, one message at a time.
- At least 30 s between any two sends (also across jobs). Each gap is random within the job's range.
- 0–60 s random jitter on start time; 2–5 s "typing…" before each message.
- Daily cap (default 30, max 60). Over the cap, the rest continues after midnight IST.
- Sends only to groups the number is currently a member of (checked right before sending). Unknown groups are skipped.
- Each job × group is sent at most once, even after restarts or crashes.
- WhatsApp disconnected → the queue waits. A job more than 120 min late (configurable) is marked *missed*, not sent at an odd hour.
- A failed send is retried once after ~90 s, then marked failed.

## Security

- HTTPS via Coolify, `HttpOnly; Secure; SameSite=Strict` session cookie, custom-header CSRF check, strict CSP, no framing.
- bcrypt passwords (min 10 chars), lockout after 5 wrong tries (15 min), login rate limit, 12 h idle timeout.
- Admin vs member roles; every action is in the activity log.
- Secrets are generated by Coolify (`SERVICE_PASSWORD_*`), never stored in git. The engine key is shared only on the private network.
- No "anti-ban" packages, pinned dependencies, both containers drop Linux capabilities, app container is read-only.

## Coolify setup (once)

1. New resource → Private repository (GitHub App) → this repo, branch `main`, build pack **Docker Compose**, file `/docker-compose.yml`.
2. Domains: `wabox` service → `https://wabox.example.com/wabox`. Leave `engine` **without** a domain.
3. Deploy. Coolify generates `SERVICE_PASSWORD_64_ENGINEKEY` and `SERVICE_PASSWORD_ADMIN`.
4. DNS: `wabox.example.com` A record → the server IP.

Data lives in the `engine-data` (WhatsApp login) and `wabox-data` (jobs, users, logs) volumes. Back them up with Coolify's volume backups.


## Local run (dev)

```bash
cd app && npm ci
WA_ENGINE_URL=http://localhost:3100 WA_ENGINE_KEY=... ADMIN_PASSWORD=change-me-now COOKIE_INSECURE=true DATA_DIR=./data npm start
# open http://localhost:3000/wabox/
```

## The engine (replaces Gateway)

`engine/` is a ~400-line service around `whatsapp-web.js`. It does the jobs Gateway used to do:

| Job | How |
|---|---|
| Keep the login | Stored on the `engine-data` volume; restarts reuse it, no new QR. |
| Self-heal | Reconnects after a drop; retries a failed start with backoff (30 s → 5 min); restarts Chrome after 3 failed health checks, above `CHROME_MAX_MB`, and nightly ~04:00 IST when idle. Never restarts mid-send. |
| Pin a known-good WhatsApp Web | Records the version every time it connects. After 2 failed starts it retries pinned to the last good version. `WA_WEB_VERSION` forces one. |
| Locked-down Chrome | Non-root, read-only filesystem, all Linux capabilities dropped, no published ports, memory/process limits. |
| Private API | Every call needs `ENGINE_API_KEY` (generated by Coolify). Image links to private addresses are refused. |

Error contract with WA Box: **4xx = definitely not sent**, anything else = maybe sent (WA Box checks the chat before doing anything). Both sides have tests for it (12 engine, 26 app), and both run during the Docker build.

**If WhatsApp Web changes and sending breaks:** the engine first retries on the last good version automatically. If that's not enough, update `whatsapp-web.js` in `engine/package.json` to the newest release and push; Coolify rebuilds.

## Images and links
- **Upload an image**: kept only until it's no longer needed, 3 days after a one-off message finishes (so "Send again" still works). Weekly messages keep theirs until stopped. Unused files are cleaned up hourly.
- **Image link**: nothing is stored. The link is checked when you schedule (public? an image? under 5 MB?) and the image is fetched at send time. Public Google Drive file links are converted automatically.
- **Links in text**: WhatsApp shows a preview card by default; it can be switched off per message. Short links (bit.ly etc.) and messages with many links get a spam warning.
